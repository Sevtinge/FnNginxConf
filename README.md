# FnNginxConf（飞牛Nginx转发）· Nginx 反代管理

> 包名 `FnNginxConf`，应用中心显示名「飞牛Nginx转发」，网关入口 `/app/FnNginxConf`。

可视化设计并注入飞牛 Nginx 反向代理配置：只需填写 **名称 / 路径 / 目标地址**，即可生成 `conf.d` 配置并持久化到 `ng.conf.zip`。

---

## 项目核心能力（能做什么）

本应用核心用途：**将飞牛 OS 域名 / IP 下的子路径反向代理转发至自定义本地服务端口或 Unix Socket，直接通过飞牛 OS 网关子路径访问内网自建服务**

### 80/443 按规则路径智能转发
飞牛系统默认会把 80/443 的请求统一 302 到 5666/5667 网关端口。应用配置规则后，会同时给 `nginx.conf` 打一个可逆补丁：

- 规则路径命中且目标为**可直连的 HTTP/HTTPS 地址**（非 80/443、非回环地址、目标不带子路径）时，80/443 直接 302 到目标地址，例如 `/olink` → `http://cloud.sevtinge.com:5512/...`；
- 其余请求保持系统原行为，仍跳转到 5666/5667 网关；
- Unix Socket 规则、目标为 80/443、回环地址或带子路径的目标，继续走 5666/5667 代理，避免回环或路径语义偏差。

补丁会随 `conf.d` 一起持久化到 `ng.conf.zip`（`nginx.conf` 条目，并保留一份原始 `nginx.conf` 备份），应用失败自动回滚；移除全部规则或卸载应用时自动还原原始 `nginx.conf`。

### 子路径反向代理挂载
支持自定义飞牛访问子路径，实现 `https://飞牛IP:端口/自定义路径` 转发到任意本地后端服务：
   - 示例：配置路径 `/myapp`，目标地址 `http://127.0.0.1:8080`
   访问 `https://192.168.1.100:5000/myapp` 即可直达本机 8080 端口服务；
   - 同时支持 Unix Socket 后端转发，适配飞牛内部容器 / 进程服务。
   
## ⚠️ 系统风险与影响（使用前必读）

本应用会**直接修改飞牛系统级 Nginx 配置**并**重启系统 Nginx 服务**，请务必理解以下影响：

### 1. 以 root 身份运行
- 为写入 `/usr/trim/nginx/conf/` 并重启 `trim_nginx`，应用进程以 **root** 运行。
- 已通过**严格输入校验**（拒绝 `;{}#"'\`?` 等字符，无法注入 nginx 指令）、**管理员门禁**、纯标准库降低风险；但 root 权限本身仍是最大潜在面。

### 2. 修改的系统文件
| 文件 | 操作 | 说明 |
|---|---|---|
| `/usr/trim/nginx/conf/conf.d/fnnginx_conf.conf` | 写入/删除 | 你的全部反代规则集中在一个文件，nginx 加载它 |
| `/usr/trim/nginx/conf/nginx.conf` | 可逆补丁/还原 | 80/443 按规则路径智能转发，其余请求保持原跳转 |
| `/usr/trim/share/.restore/ng.conf.zip` | 增删条目 | 持久化到恢复包，保证重启/恢复后配置仍在 |
| `systemctl restart trim_nginx` | 重启 | 让新配置生效 |

- **只增删自己的 `conf.d/fnnginx_conf.conf` 条目，并只对 `nginx.conf` 做带标记的可逆补丁**，官方和其他应用注入的配置一律不碰（实测其他条目字节不变）。
- 每次写 zip 前自动 `.bak` 备份 + 写入后自检读回，损坏则放弃并回滚。

### 3. 重启 Nginx = 整个 NAS Web 访问短暂中断
- 点击「应用配置」会在**后台重启 `trim_nginx`**，期间（约 1 秒）NAS 的 Web 界面、应用中心、其他经网关的应用会**短暂无法访问**。这是让新反代生效的必要步骤。
- 前端已改为**异步提交**：立即返回结果，重启在后台完成，不会出现"请求中断/失败"假象。

### 4. 出错有保护（不会让系统长期处于坏配置）
- 应用前先 `nginx -t` 校验系统当前配置，**系统本身已异常时拒绝应用**。
- 写入后再 `nginx -t`，失败立即回滚（磁盘文件 + zip 从 `.bak` 恢复）。
- 若系统 Nginx 已被其他原因弄坏，本应用会拒绝叠加并明确报错。

### 5. 已知平台限制（无法规避）
- **socket 权限 0666**：本机任意进程可直连应用的 unix socket 并伪造管理员头——这是飞牛统一网关模型的固有边界，网关登录校验是第一道防线。
- **不做的事**：不读取/不修改用户文件、不监听外网端口、不改变官方配置行为。

## 功能

- **三条信息即可配置**：名称、路径、目标地址（HTTP 地址 或 Unix Socket）。
- **路径冲突保护**：自动扫描官方 nginx 配置，拒绝与系统已有 location 冲突。
- **统一网关接入**：`/app/FnNginxConf`，带 NAS 登录态校验；写操作仅管理员可用。

## 路径挂载常见问题（重要）

### ① 单页应用挂到子路径 → 资源 404（`/assets/...`）

**现象**：页面能打开（HTML 正常），但 CSS/JS 报 `GET https://你的NAS/assets/index-xxx.js 404`。

**根因**：目标应用（如 Vite 构建的 SPA）的 HTML 里资源用的是**根路径绝对地址**（`src="/assets/..."`）。挂到 `/mp` 后，浏览器会去请求 NAS 根路径的 `/assets/...`，根本不经过你的 `/mp` 规则，所以 404。

**解决**：在目标应用里配置 **base path** 后重新构建，例如 Vite：

```js
// vite.config.js
export default defineConfig({ base: '/mp/' })
```

重新构建后资源路径变成 `/mp/assets/...`，就会走你的反代规则正常加载。

> 飞牛 nginx **未编译 `sub_filter` 模块**，因此代理无法在返回 HTML 时重写资源路径——这类问题只能靠应用侧 base path 解决，反代硬修不了。

### ② 前缀剥离 / 保留

「去掉路径前缀」（高级选项）决定后端收到的 URL 带不带挂载前缀：

| 目标服务形态 | 选项 | 后端收到的路径 |
|---|---|---|
| 挂在根路径（访问它首页就是 `/`） | ✅ 勾选（默认） | `/路径/xxx` → `/xxx` |
| 自身配置了基础路径（Base URL = 该前缀） | ⬜ 不勾选 | `/路径/xxx` 原样转发 |

### ③ 路径与官方系统冲突

应用会自动拦截以下情况，防止抢占系统服务：
- **保留命名空间**：`/app/`（统一网关）、`/cgi` —— 任何子路径都不允许占用。
- **完全相等**：与官方 location 相同（如 `/music`、`/docs`、`/vm`、`/s/`、`/websocket` 等）→ 拒绝。
- **子路径**：位于官方路径之下（如 `/music-enhance/` 在 `/music` 之下）→ 非阻塞提示（nginx 最长前缀匹配可共存，与 FnMusicEnhance 现有模式一致）。

## 使用

1. 打开应用中心 → 飞牛Nginx转发 → 进入管理页面（`/app/FnNginxConf`）。
2. 点「新增规则」，填写 **名称 / 路径 / 类型 / 目标地址（或 socket 路径）**。
3. 点「应用配置」——后台完成：生成 conf.d + 补丁 nginx.conf → `nginx -t` 校验 → 同步 `ng.conf.zip` → 重启 `trim_nginx`。前端轮询显示结果。

## 生成示例

```nginx
# Generated by FnNginxConf - DO NOT EDIT
location /music/ {
    proxy_pass http://unix:/var/run/xxx.sock:/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

## 构建与自动发布

### 本地构建

```bash
fnpack build --directory .
# 产物：FnNginxConf.fpk（按版本重命名：FnNginxConf-<version>.fpk）
```

### 自动构建（GitHub Actions）

`.github/workflows/release.yml` 已配置：**推送 `main`/`master` 或手动触发 `workflow_dispatch`** 时：

1. 安装 `fnpack`（Linux 版）。
2. 从 `manifest` 读取版本号。
3. 校验打包文件齐全（`manifest`/`config`/`app`/`cmd`/`wizard`）。
4. `fnpack build` 生成 `.fpk`，按版本重命名为 `FnNginxConf-<version>.fpk`。
5. 发布到 GitHub Release（tag `v<version>`，同名 tag 不存在时自动创建）。

## 本地预览（无飞牛设备）

```bash
cd app/server
# 指向本机官方配置副本可启用冲突检测
export TRIM_CONF_DIR="C:/Users/HQL/Desktop/nginx/ng.conf/conf.d"
export TRIM_NGINX_CONF="C:/Users/HQL/Desktop/nginx/ng.conf/nginx.conf"
export PORT=9000
export RULES_FILE="$TEMP/fnnginx_rules.json"
python server.py   # 访问 http://127.0.0.1:9000/ 或 http://127.0.0.1:9000/app/FnNginxConf/
```

> Windows 本地无 nginx，`应用配置` 会以「nginx 配置校验失败」优雅返回（不会破坏任何东西）；完整流程需在飞牛真机验证。

## 卸载

卸载时（`cmd/uninstall_init`，在文件删除前执行）自动 **best-effort 删除已注入的 nginx 配置**：移除 `conf.d/fnnginx_conf.conf` 文件、还原 `nginx.conf` 补丁、从 `ng.conf.zip` 删除对应条目、重启 `trim_nginx` 释放配置——反代规则不会在应用卸载后残留。清理失败不会阻断卸载（`|| true` 兜底）。
